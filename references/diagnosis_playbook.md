# 自动化诊断作战手册（经验单）

> 任何"页面卡死 / 按钮失效 / 元素找不到 / 投递无记录"的排查，**先按下方 SOP 走一遍**，再下"BOSS 改版/UI 变更"之类的结论。本手册全部条目均经 `evaluate` 返回的 DOM 文本/结构证据验证，非截图推断。

## 0. 快速诊断 SOP（出问题时照做）

1. **探活 + 建活页**：`list_tabs` 看 `agent:boss-main` 是否有活跃标签页；无则 `ensure_active_tab()`（会 `navigate` 到 zhipin 建页）。**会话 `tabs:[]` 时一切 DOM 诊断都是假象**。
2. **确认页面在目标状态**：`evaluate("window.location.href")` 与关键文本（如"推荐""算法工程师"），确认不是停在登录页/空白页。
3. **面板类问题先排除死会话**，再判"卡 loading"（见经验单5）。
4. **点击无响应先查上限模态**（见经验单3），再疑选择器/机制。
5. **核对投递状态用直连只读探测**（见经验单2），不靠间接证据。
6. 所有结论必须有 `evaluate` 文本/JSON 证据；**模型无法直接看截图**（见经验单4）。

## 经验单 1：诊断前先确认 WebBridge 会话有活标签页（死会话假象）

- **适用场景**：任何用 `evaluate` / `click` / `screenshot` 排查"页面卡死 / 按钮失效 / 元素找不到"之前。
- **问题**：WebBridge 会话 `agent:boss-main` 当前 `list_tabs` 返回 `tabs:[]`（无活跃标签页）时，所有 DOM 诊断返回空或假数据，极易误判为"BOSS 改版 / 页面坏了 / 面板抓取失效"。2026-10-12 深夜曾据此误下"BOSS 推送 UI 变更破坏自动化"的错误结论，浪费多轮诊断。
- **解决方案**：
  - 先 `health_check()` 或 `list_tabs` 确认会话在线且**有标签页**；
  - 无标签页时先 `ensure_active_tab()`（`webbridge_client.py`）——它会 `navigate` 到 `https://www.zhipin.com` 创建标签页，再 `evaluate("1+1")` 验证可交互。
- **注意事项**：
  - 跨调用（尤其长时间静置、`kimi-webbridge` 守护进程被取消后、浏览器被关/崩溃）会话极易丢失标签页；**每次重连后第一件事是探活 + 建页**，不要沿用上一次成功的"旧会话"经验。
  - 不要把 `tabs:[]` 与"登录过期"混淆；前者是会话无页，后者是 URL 跳 `passport`/`login`。

## 经验单 2：区分"已投递"与"未投递"——直连 URL 只读探测按钮文案（金标准）

- **适用场景**：核对某岗位是否真已投递、排查 `failed` 记录是否为假阴性、补投前确认状态、批量审计 17 条 failed。
- **问题**：反复点击试探会发出多余招呼 / 触发限流；凭 `missing=delivery_page` 等间接证据误判，把"已沟通"岗位误记成失败（如 地平线 地瓜机器人，按钮实为"继续沟通"却记成 failed）。
- **解决方案**（零点击、零副作用）：
  ```python
  navigate(f"https://www.zhipin.com/job_detail/{jid}.html", wait_range=(4,5))
  time.sleep(3)  # 页面渲染按钮需 3–4s
  bt = evaluate(r"(function(){var b=document.querySelector('.btn-startchat')||document.querySelector('.op-btn-chat');return b?(b.textContent||'').trim():null;})()")
  # bt == '继续沟通' -> 已投递（金标准）；bt == '立即沟通' -> 未投递
  ```
- **注意事项**：
  - 该探测**只读不点**，不计入任何统计、不向 recruiter 发消息；可安全批量跑（17 条约 2–3 分钟，注意单次超时）。
  - jid 取自已记录的 `stream_progress.json` / `surface_cache.json`，不要凭记忆；页面需先 `wait` 再读，否则按钮区未渲染会得到 `None`。

## 经验单 3：点击"立即沟通"无响应 ≠ 选择器失效——先查"每日沟通上限"模态

- **适用场景**：点击立即沟通 / 投递按钮后，按钮文案不变、无聊天页跳转、无可见弹窗（rect 检测为 `[]`）、`chatVisible=false`。
- **问题**：最易误判为"BOSS UI 变更 / 点击机制失效"。真实根因往往是 **BOSS 每日首联上限（150/天）已打满**——点击会弹出"沟通上限"模态，但与普通打招呼弹窗不同，刚出现时带淡入动画（rect 可能为 0），纯按 `getBoundingClientRect().width>0` 检测会漏掉。
- **解决方案**（DOM 文本铁证，非截图）：
  ```python
  click(".btn-startchat, .op-btn-chat")   # 触发
  time.sleep(4)                            # 关键：延时等模态稳定渲染（动画期 rect=0）
  body = evaluate("document.body.innerText") or ""
  if "上限" in body or "150位BOSS" in body:
      # 命中每日上限模态，停止当天投递，次日重置再补
  # 也可用固定/绝对定位且尺寸>150 的可见层扫描（更稳）：
  #   dialog-wrap.greet-pop / dialog-container 内含文案
  ```
  上限模态真实文案：**「您已达到沟通上限 您今天已与150位BOSS沟通，休息一下，明天再来吧～ 确定」**；类名 `.dialog-wrap.greet-pop` 与 `.dialog-container`。
- **注意事项**：
  - 命中上限即**停止当天所有投递**，不要循环重试——只会持续弹窗、零收益。
  - 上限按自然日重置（约午夜），次日恢复路径：直连 `job_detail/{jid}.html` → 点 `.btn-startchat`，上限重置后应正常触发（参照"继续沟通"点击成功跳 `/web/geek/chat` 的路径）。
  - 上限模态与"打招呼"对话框不同：前者=当日终止信号，后者=首联正常流程（需发问候或点确定才完成），勿混为一谈（见经验单6）。

## 经验单 4：模型无法直接看截图——DOM 文本/结构化数据才是可靠证据

- **适用场景**：想用 `screenshot` 确认页面状态、弹窗、按钮文案时。
- **问题**：多模态读图在本环境被过滤（`content filtered`），`screenshot` **不能替代** DOM 证据；仅凭"假定弹窗长这样"下结论会出错（如误把上限模态当作"UI 变更"）。
- **解决方案**：一切结论以 `evaluate` 返回的 JSON / 文本为准；截图只作为给用户核对的产物。检测弹窗用 `document.body.innerText` 关键词扫描 + 固定/绝对定位且尺寸 >150 的可见层扫描，而非依赖看截图。
- **注意事项**：在文档/复盘里写"页面显示 X"前，必须有对应的 `evaluate` 文本证据支撑；不要假设截图内容。

## 经验单 5：推荐页面板切换间歇性"卡 loading"——属慢加载非硬故障

- **适用场景**：点击推荐页（/web/geek/jobs）其他卡片后，右侧详情面板长期停在 `.job-detail-loading`（含 `<canvas class="load_placeholder">`）骨架，`descLen=0`。
- **问题**：误判为"BOSS 改版破坏面板抓取"。实测同一活页下，部分卡片 3s 内正常加载（`descLen>50`，如 card#1），部分偶发卡在 loading 骨架（如 card#14）——是间歇性慢加载，不是硬故障。与死会话叠加会放大误判。
- **解决方案**：轮询等待；`loading=true` 且 `descLen<=50` 持续 **25s** 才判失败；可重试点击同卡 / 换卡；需要稳定可探测时改用**直连 `job_detail/{jid}.html`** 路径（面板必渲染、按钮文案可零点击读取，见经验单2）。
- **注意事项**：先按经验单1排除死会话，再判面板问题；不要把"偶发慢"当成"必然坏"。

## 经验单 6：首次联系（立即沟通）与续联（继续沟通）的点击行为不同

- **适用场景**：编写 / 修复投递与恢复脚本的点击与证据判定逻辑时。
- **问题**：同一 `.btn-startchat` 选择器，点击"立即沟通"（首联）会弹**打招呼对话框**或**上限模态**；点击"继续沟通"（已联）直接跳聊天页（`/web/geek/chat`）。用一套证据逻辑会漏判成功或误判失败。
- **解决方案**：点击后按四类信号判定——
  1. **上限模态**（文案含"沟通上限"/"150位BOSS"）→ 当日终止信号，停止投递；
  2. **"留在此页"按钮**（`stay_btn`，路径B 成功信号，v5.6.1 起为权威）；
  3. **聊天页跳转**（`url` 含 `chat` 或 `chatVisible`）；
  4. **会话列表匹配**（`chat_list_match`：目标公司 + 送达/您好）。
  建议 `deliver_engine.py` 新增 `daily_limit` 检测分支：点击后立即延时扫 `body.innerText`，命中上限则记 `blocked`/上限并返回，避免空转。
- **注意事项**：首联若弹"打招呼"对话框（**非**上限），需发送招呼或点确定才完成投递；不要把它和上限模态混为一谈。恢复 16 条被上限拦截的岗位时，上限重置后点"立即沟通"走的是首联流程，要走完打招呼/留此页才算成功。

## 经验单 7：安全验证页 = 零卡片，别误判成"虚拟滚动导致卡片不在 DOM"（2026-10-13）

**现象**：整批后段连续 `READ_FAILED: ... no_link_match`，看起来像"虚拟滚动把卡片回收了"。

**真因**：高频读 JD 触发 BOSS 风控，页面被整页跳转到
`https://www.zhipin.com/web/passport/zp/verify.html?...`，标题「安全验证 - BOSS直聘」。
此时 DOM 里一张岗位卡都没有，所以每条都是 `no_link_match`。

**验证方法（纯 DOM，不点任何东西）**：
```
evaluate('window.location.href')   → 含 /web/passport/zp/verify
evaluate('document.title')         → 安全验证 - BOSS直聘
```

**正确处理**：立即停批、停止一切点击，**交回用户人工完成验证**。继续重试只会加重风控、拉长封禁。
代码侧已落地：`webbridge_client.is_verification_page()`，由 `serial_loop.step_read` 与
`batch_deliver` 每轮前置调用，命中即停（`⛔ 检测到 BOSS 安全验证/风控拦截，立即停止本批`）。

**区别诊断**：连续 3 条 READ_FAILED 时先判验证页；若不是验证页，才是"虚拟滚动窗口已过"，
处置是 `--step refresh` 后重建候选池再投，而不是继续空跑。

## 经验单 8：岗位是"滚"出来的，不是"刷"出来的——先怀疑计数，别先怀疑供给（2026-10-13）

**核心事实（用户指正 + 实测）**：BOSS 岗位列表是**无限滚动**，一路往下滚就持续出新岗位，
跟刷抖音一样。实测一次连续滚动拿到 **330 张卡**（15→30→45→…→330）。**滚动是主要供给方式**。

**曾经的误判**：Agent 滚出 15 张就不动了，判定"频道岗位耗尽"，于是去换频道 / 换城市 / 走搜索页
（都是越权或死路）。**真因不在供给，在两处代码**：
1. `_count_cards()` 硬编码 `.job-card-wrap`，同一页面实际 30 张只数到 15，滚动后数字恒定
   → 连续 4 次"无新增" → **假穷尽**。现按**唯一 jobId** 计数，并兼容 `li.job-card-box`。
2. `MAX_SCROLLS_PER_BATCH` 原为 8，每批只滚 8 次就停，又没有反复续跑 `next-batch`，
   于是在 60 张处"以为到底"。现已提到 **20**，全局上限 80，反复跑 `next-batch` 可一路滚下去。

**正确处理顺序**：
1. 滚动（反复 `--step next-batch`）→ 主力，能出几百条。
2. 滚动确实停摆（命中底部标记「没有更多了」/ 连续无新增 / 已到全局上限）→ 才用 `--step refresh`
   重新进频道换一批（兜底，实测每轮仍能出 19–29 条新货）。
3. 连续 3 轮 refresh 无新货 = 真穷尽 → 停下汇报，**不换频道、不换城市、不走搜索页**
   （搜索页点卡片会跳转 job_detail，`step_read` 依赖"原地加载右侧面板"，实测 ~100% READ_FAILED）。

**一句话**：报"穷尽"时先问「数对了吗？滚够了吗？」，再问「是不是真的没岗位了」。
